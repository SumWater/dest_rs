# 实验现状与后续计划

本文档用于记录当前实验结果、与开题报告的对应关系、需要保留的实验、需要重新定义并重跑的实验，以及后续论文撰写前建议补充的分析。

## 1. 当前实验整体判断

当前项目已经实现并运行了开题报告中设想的主要技术路线：LoRA、strategy-specific Prefix、Prefix+LoRA 混合、局部-全局正交约束、策略分类辅助监督，以及基于 swap samples 的策略控制评估。

从 `output/need/casino_augmented` 中已有结果看，B2-B6 可以支撑一个明确结论：完整 DeST-RS 目前没有超过 Prefix-only；相反，实验显示 Prefix 更适合承载策略控制，LoRA 更适合降低生成损失，但二者联合训练会削弱细粒度策略控制。

这与开题报告中“完整方案提升策略一致性”的预期不一致，但仍然没有偏离开题范围。开题报告研究的是谈判对话中的 PEFT 策略可控生成，当前实验可以转向“混合 PEFT 的功能分工与干扰机制分析”。

## 3. 可以保留、不需要改动的实验

B2-B6 是当前最可靠的主实验，可以保留为论文中的核心消融。

- B2 `lora_only`：只训练 LoRA。结果表明 LoRA 能较好降低 PPL，但策略控制能力很弱。
- B3 `prefix_only`：只训练策略 Prefix。结果表明 Prefix 的细粒度策略控制最强，但生成 PPL 较高。
- B4 `prefix_lora`：同时训练 Prefix 和 LoRA。结果表明生成质量接近 LoRA，但 9 类策略控制弱于 Prefix-only。
- B5 `prefix_lora_orth`：在 B4 基础上加入正交约束。结果表明当前正交设置没有提升细粒度策略控制。
- B6 `dest_rs`：在 B5 基础上加入策略分类辅助监督。结果表明当前完整 DeST-RS 未能超过 Prefix-only。

论文中可以围绕 B2-B6 写出以下主结论：

1. Prefix 是当前策略控制的主要来源。
2. LoRA 主要改善生成适配和 PPL。
3. Prefix+LoRA 联合训练存在策略信号干扰。
4. 当前正交约束和分类辅助监督未能充分缓解该干扰。
5. 生成质量与策略一致性之间存在明显 trade-off。

## 4. 需要重新定义并重跑的实验

旧版 B7-B9 的问题在于：代码把“模块是否启用”和“模块是否训练”绑定在 `adapter_mode` 上。

例如，旧版 B8 写成 `adapter_mode = prefix_only`，代码会关闭 LoRA，因此它不是严格的“加载并冻结 LoRA 后训练 Prefix”。旧版 B9 写成 `adapter_mode = lora_only`，代码会关闭 Prefix，因此它也不是严格的“加载并冻结 Prefix 后训练 LoRA”。

现在代码已经改成可以分别控制：

- `enable_prefix`：前向和生成时是否启用 Prefix。
- `enable_lora`：前向和生成时是否启用 LoRA。
- `train_prefix`：是否更新 Prefix 参数。
- `train_lora`：是否更新 LoRA 参数。
- `train_classifier`：是否更新策略分类头。
- `warm_start_prefix`：是否从 warm-start 目录加载 Prefix。
- `warm_start_lora`：是否从 warm-start 目录加载 LoRA。

## 5. 需要补充的实验和分析

### 5.1 扩大策略控制评估样本

当前 `demo_num_examples = 5`，即 5 个 valid 样本 × 9 个策略 = 45 条生成。这个数量太小，不足以支撑稳定结论。

建议后续至少改为：

- 30 个样本 × 9 个策略 = 270 条；
- 或 50 个样本 × 9 个策略 = 450 条。

这样策略准确率、4 类粗粒度准确率和策略级 breakdown 才更有说服力。

### 5.2 策略级 breakdown

目前结果显示很多生成会被评估器判成 `self-need` 或 `small-talk`。后续需要统计每个目标策略的准确率和混淆方向，例如：

- 哪些策略最容易被 Prefix 控制；
- 哪些策略经常被误判为 `self-need`；
- `other-need`、`uv-part`、`vouch-fair` 是否天然更难区分；
- 加 LoRA 后哪些策略下降最明显。

### 5.3 生成质量与策略一致性的 trade-off

需要把 PPL 与策略准确率放在同一张图或同一张表中分析：

- LoRA-only：PPL 好但策略控制弱；
- Prefix-only：策略控制强但 PPL 差；
- Prefix+LoRA：PPL 接近 LoRA，但策略控制下降；
- Orth/CLS：当前没有解决二者冲突。

这个 trade-off 是论文中最有价值的分析点之一。

### 5.4 典型案例分析

从 `swap_samples_valid.jsonl` 中选取 3 到 5 个上下文，展示不同策略下的生成。

建议选择：

- Prefix-only 控制明显的案例；
- Prefix+LoRA 控制变弱的案例；
- DeST-RS 生成质量较好但策略不够准的案例；
- 容易混淆的策略案例，例如 `self-need` vs `uv-part`，`promote-coordination` vs `vouch-fair`。

### 5.5 正交约束机制分析

如果论文仍保留正交约束作为方法组成，需要补充中间层表示分析：

- Prefix delta 与 LoRA delta 的 cosine similarity；
- 加 Orth 前后 similarity 是否下降；
- similarity 下降是否真的带来策略准确率提升；
- 若没有提升，需要解释“几何正交不等于功能解耦”。

## 7. 论文叙事建议

不建议继续把论文主张写成“DeST-RS 完整方法显著优于所有基线”。当前更稳妥、更诚实的主线是：

> 本文围绕谈判对话策略可控生成，系统研究 Prefix、LoRA 及混合 PEFT 的功能分工。实验发现，Prefix 更适合承载细粒度策略控制信号，LoRA 更适合提升语言建模与任务适配能力，但二者联合训练会引入策略信号干扰。当前局部-全局正交约束与策略分类辅助监督未能充分缓解该干扰，说明混合 PEFT 中的几何解耦与功能解耦之间仍存在差距。

这条路线与开题报告保持一致，因为研究对象、技术组件、实验体系和问题范围都没有改变；改变的是最终结论从“提出一个效果最优的方法”调整为“通过系统实验揭示方法边界与干扰机制”。


 不改代码的话，我觉得 B6 目前“不可能稳定最好”的主要缺陷有这些，按重要程度排：

  1. B6 的训练目标和最终评估目标不完全一致。
  B6 加的是 orth_loss + cls_loss，但最终策略控制评估看的是“生成文本被 LLM 判成目标策略”。分类头只是在训练时约束
  hidden state，不参与生成；所以分类准确不等于生成策略准确。你现在 B6 的 cls_loss 很快降得很低，但生成策略准确率没提
  升，说明分类头可能只是学会了识别内部表示，没有把策略信号有效传到输出文本。

  2. 正交约束太弱，基本像没起作用。
  B6 里 lambda_orth = 0.05，而实际 train_orth_loss 大概只有 0.001~0.002。乘起来贡献只有 0.00005~0.0001 量级，相比生
  成损失 1.x 几乎可以忽略。它很难真正改变 Prefix 和 LoRA 的关系。

  3. B6 的分类监督实现不够稳定。
  代码里有个细节：

  - 计算 orth 的 step 上，分类头用的是 delta_prefix。
  - 不计算 orth 的 step 上，分类头用的是 h_real，也就是 both-on 的真实 token hidden state。

  而 B6 默认 orth_every_n_steps = 20，所以绝大多数 step 分类监督其实不是直接压在 delta_prefix 上。这会让“分类监督增
  强 Prefix 策略表征”的设计目标打折。

  4. LoRA 可能过强，覆盖了 Prefix 的策略信号。
  B2/B4/B5/B6 的 PPL 都明显优于 B3，说明 LoRA 很会拟合回复分布。但策略准确率反而下降，说明 LoRA 学到的“常见回复模
  式”可能压过了 Prefix 的策略差异。B6 如果不限制 LoRA 的影响，很难比 Prefix-only 更会控制策略。

  5. B6 同时优化多个目标，但没有做权重搜索。
  现在 B6 固定是：

  lambda_orth = 0.05
  lambda_cls = 0.2

  这个设置不一定合理。B6 不好不能说明思路一定错，只能说明当前权重下没跑出来。尤其分类监督可能偏弱，正交项更明显偏
  弱。

  6. 评估样本太少。
  现在策略评估是 5 个 valid 样本 × 9 策略 = 45 条。这个数量太小，B6 和 B4/B5 的差距可能有波动。不过 B6 明显低于 B3，
  这个趋势还是值得重视。

  7. B6 可能用的是最终 checkpoint 做生成，而不是最佳 valid checkpoint。
  训练过程中保存过 best checkpoint，但后面生成 swap_samples_valid.jsonl 时用的是训练结束时内存里的最终模型。比如 B6
  最好 valid loss 在 epoch 1，但最终生成可能用 epoch 2。这个会影响策略评估结果。

  所以如果你希望 B6 最好，后续实验上应该优先检查这些方向：

  1. 增大或扫描 lambda_cls，比如 0.5 / 1.0 / 2.0。
  2. 增大或扫描 lambda_orth，比如 0.1 / 0.5 / 1.0，现在太小。
  3. 让分类监督稳定作用在 delta_prefix 上，而不是大多数 step 作用在 h_real 上。
  4. 降低 LoRA 强度，比如减小 lora_r、降低 LoRA 学习率，或先训练 Prefix 再轻量训练 LoRA。
  5. 扩大 swap eval 样本到至少 270 条。
  6. 用 best checkpoint 生成 swap samples，而不是最终 epoch。
  7. 做 B6 的超参数版本，不要只靠当前这一组 B6 下结论。

  一句话：B6 现在不是”方法必然不行”，而是当前实现和超参数更偏向优化生成损失，没有足够强地保护 Prefix 的策略控制信
  号。

## 8. 补充实验方案（2026-06-14）

### 8.1 B6 崩溃的根因分析

经代码审查，确认 `src/losses.py` 中 `compute_delta_prefix_hidden()` 存在梯度 bug：

```python
# 第一个前向（base-only）：正确包在 torch.no_grad() 中
with torch.no_grad():
    ...  # h_base 已 detach

# 第二个前向（prefix-only）：❌ 没有 torch.no_grad()
with lora_disabled_ctx(...):
    ...  # h_prefix 在计算图中，有梯度！
```

**后果**：在非 orth step（每 20 步中的 19 步）上，`cls_loss` 的梯度通过 prefix-only 前向路径反向传到 `prefix_bank`，与 `gen_loss` 通过 both-on 路径传来的梯度在 `prefix_bank` 上叠加。两股梯度来自不同的前向路径（一个 LoRA 开、一个 LoRA 关），对 prefix 的优化方向互相矛盾，导致 prefix_bank 被推离适合生成的方向，gen_loss 从正常的 ~1.2 爆炸到 13.9。

**修复**：将第二个前向也包入 `torch.no_grad()`，使 `compute_delta_prefix_hidden` 的返回值完全 detach。修复后，非 orth step 上 cls_loss 只训练分类头；orth step 上 cls_loss 通过 orth 路径统一作用于 prefix。
